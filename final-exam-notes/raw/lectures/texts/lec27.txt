Gustafson’s Law
• While Amdahl’s Law often feels like a pessimistic view of
parallel computing, focusing on the limitations caused by
serial bottlenecks.
• Gustafson’s Law (also known as Gustafson-Barsis’s Law)
provides a more optimistic perspective that better
describes how we use HPC in the real world.
• While Amdahl's Law assumes a fixed problem size,
Gustafson’s Law assumes that as we gain more
processing power, we use it to tackle larger, more
complex problems in the same amount of time.
13

Scaled Speedup
• Users rarely run a small problem on a massive
supercomputer just to finish it in milliseconds.
• Instead, use the extra cores to solve larger problems,
e.g., increase the resolution of a simulation, use a
larger dataset, or perform more iterations.
• In this model, the execution time is kept constant,
but the amount of work performed increases –
referred as scaled speedup.
14

Gustafson’s Law
Speedup:

Sp = p + (1 – p) f
where p is the number of processes, and f is the nonparallelizable (serial) fraction of the process.

15

Example
Q: An application executing on 64 processes requires 220
seconds to run. Benchmarking reveals that 5% of the time
is spent executing serial portions of the computation on a
single processor. What is the scaled speedup of the
application?
A:
S = 64 + (1 - 64) x (1 - 64)(0.05)
= 64 - 3.15 = 60.85

Scaled Speedup
• Unlike Amdahl's Law, which assumes fixed problem
size, Gustafson’s Law assumes scaled workloads.
• As p increases, the parallel portion grows, allowing
near-linear speedup when f is small.
• The serial fraction still limits performance, but far
less restrictively than in Amdahl’s model.

The Karp-Flatt Metric
• While the other two laws predict theoretical speedup
based on a fixed or scaled workload.
• Karp-Flatt provides a way to measure the actual
efficiency of a parallel program by looking at the
experimentally determined serial fraction.
• Reveals overheads that Amdahl’s Law often ignores, such
as communication costs, synchronization delays, and
thread creation time.

How to use the Karp-Flatt Metric
• If you are running a parallel algorithm on a cluster
and you notice that speedup is not linear, Karp-Flatt
helps you diagnose why.
– The code inherently may have a lot of serial parts
(Amdahl’s Law).
– The hardware or software stack, (e.g., MPI) is causing
delays as you add more processors.

20

Interpreting the Karp-Flatt Metric
• Calculating e for different numbers of processors,
you can identify the bottleneck
– If e remains constant as you increase the number of
processes (p), it suggests that the speedup is limited
primarily by the serial fraction of the code.
– If e increases as you increase p, it indicates that
parallel overhead is growing, showing that that the
algorithm does not scale well with more hardware.

Scalability
• A problem (or system) is scalable if it can handle
increasing problem sizes efficiently.
• This means that as the workload grows, the
algorithm or system can still process it without a
disproportionate increase in execution time.
• Scalability ensures that a system or algorithm can be
extended to larger datasets or more demanding
computations without becoming unusable.

Strong Scalability
• Efficiency remains constant as the number of
processes increases while the problem size stays the
same.
• Strong scalability shows how well a parallel system
can speed up a fixed workload.
– Measures the ability to reduce execution time by adding
more processors.

• Often limited by Amdahl’s Law, because the serial
portion of the computation eventually dominates the
total execution time.
31

Weak Scalability
• Efficiency remains constant as the number of
processes increases by increasing the problem size
proportionally.
• Reflects how a system handles growing workloads
while maintaining efficiency.
– Useful for large-scale simulations or data-intensive tasks, as
it demonstrates the system’s ability to handle bigger
problems as more resources are added.

• Overheads from communication can still limit
performance, so not all problems scale weakly.
32

In Practice …
• Understanding strong vs weak scalability helps algorithm
designers choose whether to optimize for fixed
workloads (strong) or growing workloads (weak).
• When benchmarking a parallel system, reporting both
types of scalability gives a fuller picture of its capabilities.
• Helps in deciding how many processors to allocate for a
given problem size to maximize efficiency without
wasting resources.
